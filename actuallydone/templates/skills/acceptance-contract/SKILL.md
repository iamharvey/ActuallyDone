# 验收契约

自然语言的验收标准挡不住两件事：**需求缩水**（做了三条里的两条就说完成）和**编用例名**
（清单勾了，但那个用例根本不存在）。契约把每条需求钉到一个用例名上，由脚本去核。

## 写在哪、什么时候写

`{{ACCEPTANCE_DIR}}/<任务名>.toml`，**开工前写**——写不出用例名，说明这条需求还没想清楚
怎么验证，此时就该问，而不是做完再补。交付后移到 `{{ACCEPTANCE_DIR}}/done/` 归档，
归档件不再参与校验。

```toml
task = "<任务名>"

[[item]]
"要求" = "<一句可观察的业务后果>"
test = "{{TEST_NAME_EXAMPLE}}"
impl = "{{IMPL_EXAMPLE}}"
```

`要求` 写业务后果，`test` 是{{TEST_FUNC_FORM}}，`impl` 是实现落点 `路径:行号`（可省略行号）。
**中文键必须加引号**——TOML 的裸键只允许 ASCII 字母数字与 `_` `-`，写成 `要求 = ` 会在
解析时直接报错（`gate check` 会把它当成契约不通过）。

## 校验规则

`{{ADONE}} gate verify-contract`，或跟着 `{{ADONE}} gate check` 一起跑。逐条核三件事，
任一不成立即失败：

1. `test` 在测试源码里**真实存在**——封死编用例名；
2. 该用例出现在最新回执的**通过名单**里——封死「有用例但没跑」「跑了但挂了」；
3. `impl` 路径存在且行号未越界——封死「指向一个想象中的实现」。

## 什么算可观察行为

`要求` 必须是能被断言的外部行为，不是实现细节的复述。

- 好：「定时未到点的任务不得被拉起」——可以造一个未来时间的任务，断言它没被执行。
- 好：「同一资源已有任务在执行时，新任务留在队列里」——可以查队列状态。
- 差：「优化调度逻辑」——没有可断言的对象。
- 差：「加一个 busy 判断」——这是实现手段，换个写法就不成立，用例会跟着实现一起腐坏。
- 调外部接口的需求，要求里写出要发的请求：「查物流时按运单号请求物流接口，返回接口给的状态」。
  只写「返回运输中」，写死返回值的实现也能满足。
- 规则能不能命中，要有一条走同一入口的反例。邮箱不同或标题不像时不得合并，反例同样不许事后改这些字段。
  `要求` 写清这条用例能证明什么、数据从哪条入口来。调用之后改主题、发件人、邮箱、状态再断言命中，
  证明的是「条件被凑齐」，不是契约那句话。

一条需求配一个用例。一个用例塞三条需求，等于放弃了「哪条做了哪条没做」的分辨力；
反过来一条需求配三个子用例是好的，子用例名写清各自覆盖的分支。

## 契约管一次交付，台账管整份需求

契约只覆盖手头这个任务，交付完就归档。跨迭代的那本账在 `{{REQUIREMENTS_DIR}}/*.toml`：
每条需求一个 `id`，写明 `状态`（done/partial/todo/dropped）与 `证据` 锚点，
由 `{{ADONE}} health --only requirements` 核。

```toml
[[item]]
id = "S2-034"
"需求" = "<需求原文>"
"源位置" = "<需求源文档>:85"
"状态" = "done"
"证据" = ["table:<表名>", "test:<用例名>"]
```

锚点有七类：`table:`（建表语句）、`route:`（路由注册）、`test:`（用例名，还会核它在不在
回执的通过名单里）、`view:`（前端页面文件名）、`file:`、`skill:`、`adr:`。中文键同样要加引号。

它抓的是**失联需求**：标了已做，但绑的表/路由/用例已经不在了——曾经做过，现在证据没了。
骨架用 `{{ADONE}} requirements init` 从需求源生成，机器猜的候选放在 `证据候选` 里，
**确认过才挪进 `证据`**；状态需要人工校对，没校对之前覆盖率只反映需求源里打了几个勾。
