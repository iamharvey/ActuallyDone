# 假绿检测

绿灯有两种来源：**代码变对了**，或者**门禁被改松了**。后者从输出上看和前者一模一样，
所以要靠基线比对来分辨。基线在 `{{BASELINE_PATH}}`，由脚本维护，**要入库**——
谁在什么时候放宽了什么，一眼可查。

```bash
{{ADONE}} integrity                          # 检测，约 1 秒
{{ADONE}} integrity --accept-baseline "理由"  # 记账后更新基线
```

## 七种假绿

**1. 无断言用例。** 函数体里没有任何断言（{{ASSERT_API}}），跑完必绿，什么也没证明。
冒烟用例是合理例外，但它们要么断言状态、要么在基线里明确记着。

**2. 在空集合上断言。** 最隐蔽的一种：

```
rows = 查询(...)          // 返回 0 行
for r in rows:            // 循环体一次都不执行
    断言 r.状态 == "done"
```

对策是先断言规模再断言内容：`if len(rows) == 0 { 直接失败("没有数据，用例没验到东西") }`。
构造数据的用例尤其要检查——种子没铺上、清库把数据清了，都会让集合悄悄变空。

**3. 跳过绕过。** 用例失败了，加个 {{SKIP_API}} 就绿了。检测看两处：源码里跳过的**站点数**
（抓「加个 skip」），以及回执里**运行期实际跳过数**（抓「条件跳过导致其实没跑」，
比如整包因为连不上数据库全跳）。两个数都不许无理由上涨。

**4. 断言被改弱。** `期望 == 3` 改成 `期望 >= 0`，或者把「失败」换成「打印日志」。
脚本抓不住语义变弱，这条靠评审：改动既有用例时，说明白**为什么原来的断言不再成立**。
「原来的期望值不对」要给出新期望值的推导，不能只说「跟实际对齐了」。

**5. 删用例 / 改名。** 对比基线清单，消失的用例名会被点名。合并、拆分、重命名都合法，
但必须走 `--accept-baseline` 记账，理由里写清去向。

**6. 下调覆盖率下限。** 扫 `adone.toml` 的 `coverage.threshold` 与 `tests.threshold_docs`
列出的文档里声明的百分比，低于基线即报错。{{THRESHOLD_NOTE}}

**7. 调用之后改数据凑条件。** 调用之后不许改规则要读的字段，再把结果当成规则命中。
准备数据只在调用前，走与线上相同的入口。两个记录最后同号，证明不了「决策前就是双空标题、同邮箱」。
`integrity` 抓不住这条，复核时看调用之后有没有 `UPDATE`、`$set`，或改主题、发件人、邮箱、状态。

## 基线变更的规矩

`--accept-baseline` 必须带理由，且理由写给人看：

- 好：`--accept-baseline "把 TestFoo 拆成 TestFooA/TestFooB，用例数从 388 变 389"`
- 差：`--accept-baseline "更新"` / `"修复检测误报"`

**改基线之前先问：我是在如实记录一次合理重构，还是在让红灯消失？** 如果是后者，
那要改的是代码。
