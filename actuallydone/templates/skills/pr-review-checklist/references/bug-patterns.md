# 高频 Bug 模式

<!-- 空模板。每条只收录**本项目真实发生过**的问题。
     编造的模式没人信，也占不到该占的注意力。

     格式：症状 → 根因 → 评审时怎么一眼看出来。最后一栏最重要，
     它决定了这条知识能不能在下一次评审里真的起作用。 -->

## 模板

```markdown
### <一句话描述这类 Bug>

- **症状**：线上表现成什么样（用户看到什么、数据长什么样）
- **根因**：为什么会这样
- **评审时怎么看出来**：看到什么代码形状就该警觉
- **发生过**：<日期 / issue 号 / commit>
```

## 建议优先收录的类别

- **精度与舍入**：金额用浮点、比例先乘后除、单位换算漏了倍数。
- **并发与幂等**：重复提交、任务重入、检查与写入之间有窗口。
- **边界与溢出**：空集合上的循环断言、极值、字段宽度不够。
- **状态机**：跳态、终态被改写、并发下两条路径都改状态。
- **数据迁移**：新字段没有默认值、老数据不满足新约束。
- **假实现**：调外部接口的函数返回文档里的示例值，根本没发请求；用例只断言返回值，所以是绿的。
  评审时看实现里有没有 HTTP 客户端或 SDK 调用，用例有没有断言请求本身。

写满三条以上再继续拆分文件；一开始就分太细，反而没人维护。
