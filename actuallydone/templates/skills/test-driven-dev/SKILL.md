# TDD 闭环（红 → 绿，凭证据推进）

核心约束：**「测试通过」以贴出的命令输出为准，不以你的判断为准。** 没有输出就等于这一步没做。

<!-- 这份技能是模板：方法部分（四步闭环、为什么必须先看到红）是通用的，
     但命令、路径、阈值必须换成你们项目的。带 TODO 的地方都要改。 -->

## 四步闭环

复制这份清单跟踪进度：

```
- [ ] 1. 写用例：描述期望行为，不看实现细节
- [ ] 2. 跑一次，确认它 FAIL —— 贴出 FAIL 输出
- [ ] 3. 写实现
- [ ] 4. 再跑一次，确认它 PASS —— 贴出 PASS 输出
- [ ] 5. 跑全量，确认没弄坏别人
```

### 步骤 1：先写用例

用例名与子用例名描述**业务后果**，不描述函数签名。对比：

- 差：`TestDispatch` / `t.Run("case2", ...)`
- 好：`TestDispatchSerialPerResource` / `t.Run("同一资源同时只能有一条在执行", ...)`

断言失败信息要写清「实际值 + 为什么这是问题」，而不只是 `expected 1 got 2`。

### 步骤 2：确认它会失败（不可跳过）

```bash
TODO: 单跑一个用例的命令
```

必须看到失败。看到通过有三种可能，逐个排除后才准往下走：

1. 用例断言太弱（最常见）——写了个恒真断言，或在空集合上断言。
2. 实现其实已存在——那就不是新功能，确认清楚再决定是否还要写。
3. 用例被跳过了——跳过的用例不算数。

### 步骤 3~4：写实现，再转绿

只写让用例通过所需的实现。转绿后贴出通过输出。

调外部接口时，「让用例通过」不等于返回文档里的示例值。用例断言请求真的发出去了，
响应换一个值结果跟着变，写死返回值就过不了。做法见
[completion-gate](../completion-gate/SKILL.md) 的「调外部接口要真的发请求」。

规则类需求也一样：数据在调用前经与线上相同的入口准备。调用之后不许改规则要读的字段再断言命中，
并写一条走同一入口的反例。见 [test-integrity](../test-integrity/SKILL.md)。

### 步骤 5：确认没弄坏别人

```bash
TODO: 跑全量的命令（不要用过滤参数跑完子集就宣称全量通过）
```

全量里失败的如果是与本次改动无关的既有用例，按 [completion-gate](../completion-gate/SKILL.md)
的「有用例失败，但不是这次改的」处理：先给归属证据，不停工，不修、不跳过，交付时单列。

## 验收标准（逐条勾，不满足即未完成）

```
- [ ] 目标用例在实现前失败、实现后通过，两段输出都贴了
- [ ] 全量测试通过，失败数为 0；剩下的失败只能是有归属证据的既有失败，交付时单列
- [ ] 调外部接口的实现真的发了请求，用例断言了请求本身
- [ ] 数据在调用前准备；规则类有一条走同一入口的反例
- [ ] TODO: 覆盖率不低于 ___%
- [ ] TODO: 本项目的测试约定（并发、清场、种子数据）
- [ ] {{ADONE}} integrity 无新增松动
```
